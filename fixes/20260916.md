# uf5vmjt check freeze + "sidecar restarted, run lost" — research report (2026-09-16)

Scope: RESEARCH ONLY, no source edits. Repo root `libertius`, panel `uf5vmjt/`.
Installed runtime verified: Streamlit **1.63.0**, Python 3.11.2, Go `worker` ELF binary
(`uf5vmjt/worker`, 2026-09-16 build). `st.fragment(..., run_every=...)` signature
verified present via `inspect` on the installed package.

  `uf5vmjt/lib/core/events.py`, `uf5vmjt/lib/services/netinfo.py`,
  `uf5vmjt/lib/core/config.py`, `uf5vmjt/main.py`, `uf5vmjt/lib/sections/stats.py`,

  `run_every` reruns the fragment at the interval "while the session is active";

## F1 (rank #1) — "Проверить" blocks the main script thread up to 30 s: the submit freeze

Cause: the start path runs synchronously on the full-script run inside
`with st.spinner(f"sidecar разбирает {len(lines)} строк…")`. For 200 pasted lines the
user watches exactly this spinner ("он их разбирал разбирал и в итоге ничего") while
the whole page is unresponsive, then gets either a result or a bare error.

Evidence:

- `lib/sections/check.py:153-156` — spinner + `worker_check_start(...)` called inline
  in `render_check()` (full-run context, not in a fragment/thread)
- `lib/services/sidecar.py:307-316` — `worker_check_start()` → `_worker_post(..., timeout=30)`
- `lib/services/sidecar.py:293-304` — `_worker_post`: `json.dumps(payload).encode()`,
  blocking `urllib.request.urlopen(req, timeout=timeout)`, then `r.read()` + `json.loads`
- `lib/sections/check.py:173` — only after the blocking call returns does `st.rerun()` fire

Primary source: P5 — `urlopen` timeout governs blocking operations and the call is
synchronous; P3 — Streamlit reruns the script top-to-bottom on the app thread, so a
blocking call there freezes all UI for that session until it returns (up to 30 s here,
plus Go-side parse/accept time for 200 lines before the 202 response).

Impact estimate: **highest, deterministic**. Every 200-line submit freezes the tab for
as long as the Go side takes to accept the batch (seconds; 30 s worst case on timeout).
Users perceive it as "UI freezes during checks". A transport timeout here also surfaces
as `st.error(start["error"])` (`check.py:157-159`) with no run created — matches the
"в итоге ничего" half of the complaint.

Suggested fix direction (no code): move the start call off the script thread (background
thread + placeholder status, or a fragment-owned start state); shorten/split the timeout
(connect vs. accept); consider chunked submit or an optimistic `run_id` placeholder so
the spinner text reflects real progress instead of one 30 s block.

## F2 (rank #2) — poll timeout (5 s) exceeds fragment cadence (4 s): ticks overlap and queue

Cause: the timed fragment ticks every 4 s but each tick can block up to 5 s in
`worker_check_poll`. When one poll is slow (large 200-row snapshot, busy Go side), the
next scheduled tick cannot start cleanly — fragment reruns for a session are sequential,
so polls serialize/back up and the UI stops advancing: a second, sustained freeze
*after* the run starts.

Evidence:

- `lib/sections/check.py:22` — `POLL_EVERY_SEC = 4`
- `lib/services/sidecar.py:336-338` — `worker_check_poll()` → `fetch_json(url, timeout=5)`
- `lib/services/netinfo.py:14-17` — `fetch_json`: blocking `urlopen` + full `r.read()`
  + `json.loads`, no streaming, no per-phase timeout
- `lib/sections/check.py:201-204` — `_live()` calls the blocking poll inline in the fragment

Primary source: P2 — `run_every` reruns "at the specified interval while the session is
active"; P5 — each poll is a blocking call up to its 5 s timeout. A 5 s blocking body on
a 4 s timer is a classic overlap: sustained p99 poll latency > 4 s ⇒ tick backlog ⇒ the
fragment appears frozen and every poll result arrives late.

Impact estimate: **high, load-dependent**. At 200 rows the per-poll JSON is largest and
the Go side is busiest, so this bites exactly the reported case. Even 2 consecutive
slow polls (≈8–10 s of serialized blocking) already feel like a freeze; they also feed
F3 (misses). Fixing the timeout/cadence inversion alone should remove most in-run freeze
reports.

Suggested fix direction: make timeout strictly less than cadence (e.g. poll timeout
≈2 s at 4 s cadence, or cadence 5–6 s); add a skip-if-previous-poll-still-running guard;
back off the cadence as the run ages; never let two polls overlap in one session.

## F3 (rank #3) — the 5-miss counter cannot tell "restart" from "slow/timeout": three failure modes alias to one message

Cause: `worker_check_poll` returns `{}` for **every** failure shape — transport
timeout/connection error, HTTP error, *and* a live-but-unknown run — and the fragment
counts any `{}` as a "miss". After 5 misses (≈20 s) it declares
"sidecar restarted, run lost — start again", even when the worker never restarted.

Evidence:

- `lib/services/sidecar.py:331-343` — `except Exception: return {}` (line 338-340, covers
  timeout/`URLError`/disconnect) **and** `if not data.get("run_id"): return {}`
  (line 341-342, covers a 200 response with no `run_id`)
- Worker binary (primary artifact, `strings uf5vmjt/worker`): contains the literal
  `{"error":"unknown run id"}` — i.e. the Go side answers unknown runs with HTTP 200 +
  JSON error body, which has no `run_id` key and therefore collapses to `{}` at line 341
- `lib/sections/check.py:203-221` — miss path: lines 205-213 reset the counter on any
  snapshot with `run_id`; lines 217-221 increment on any `{}` and at
  `miss >= POLL_MISS_LIMIT` (limit defined at `check.py:23`, value 5) set
  `state="error"`, `detail="sidecar restarted, run lost — start again"`
- 5 misses × 4 s cadence ≈ 20 s to the message — shorter than many real 200-probe runs

Primary source: P1 (code above) + P5 (the distinct `urllib` failure kinds — `HTTPError`
vs `URLError`/timeout — are all flattened to `{}` by the caller, so the distinction the
docs preserve is discarded one frame up).

Impact estimate: **high (diagnostic)**. This is the most probable source of the quoted
error: with F2 overlap, 5 consecutive >4 s polls time out at 5 s each and the counter
fires while the Go run is still alive. Users are then told to discard a run that may
complete seconds later. True restarts (F4) produce the identical message, so the string
has ~zero discriminating power today.

Suggested fix direction: stop collapsing — return/keep the poll failure kind
(transport-timeout vs HTTP status vs 200-`unknown run id` vs empty); use separate
counters (e.g. timeouts → "sidecar slow, still polling"; `unknown run id` repeated →
"run lost"); add a worker boot-id/uptime endpoint so "restarted" is asserted from a
fresh boot, not inferred from silence; confirm loss with one cheap `/health` probe
before flipping the run to `error`.

## F4 (rank #4) — real restarts do wipe the run registry, and there are at least five distinct restart actors

Cause: the run registry lives in Go-process memory (comment at `check.py:215`:
"Sidecar restarted (registry is in-memory)"), while the Python side spawns the sidecar
"once per Python process" (`sidecar.py:118-123`) with a module-global handle
(`sidecar.py:346`, checked at `sidecar.py:77-80`) and per-*session* "already started"
flags (`sidecar.py:130-131`, set at `161-162`). Anything that replaces the Python
process, the worker process, or the container orphans the run: the new world answers
`unknown run id` (or nothing) and F3 prints the message — this time truthfully.

Evidence (spawn/flag mechanics):

- `lib/services/sidecar.py:118-131` — `ensure_worker()`: early return if
  `worker_alive()` (line 128-129, health probe `sidecar.py:83-90`, `timeout=1` at line 87)
  or if `st.session_state.get("uf5_worker_started")` (line 130-131)
- `lib/services/sidecar.py:149-160` — `subprocess.Popen([binary], stdout=PIPE, ...)`
  + daemon `_pump_worker_logs` thread; flags recorded at `161-162`
- `lib/services/sidecar.py:17-30` — 30 s post-spawn grace (`WORKER_GRACE_SEC`, line 14)
  during which verdict failures are hidden — relevant because a fresh spawn after a real
  restart looks healthy-but-empty for 30 s
- `lib/core/config.py:79` — `WORKER_PORT` (default 6549); `main.py:57` calls
  `ensure_worker()` on every full run

Actor table (each independently orphans `run_id`):

| # | Actor | Mechanism | Primary source |
|---|-------|-----------|----------------|
| A | New browser tab / session | `uf5_worker_started` is Session State = **per tab** (P3); a second tab in the same process is saved by `worker_alive()`→healthy, but any tab opened against a fresh process/container respawns | P3 + `sidecar.py:130-131` |
| B | Cloud sleep/wake (12 h idle) | container deleted; wake = fresh process + fresh worker, empty registry; old tab's Session State may *look* alive while the run is gone | P4 + `check.py:215` |
| C | Cloud OOM / "Oh no" reboot | memory 690 MB–2.7 GB band (P4); 200-probe Go run + Python snapshot + log growth can push a small box over; reboot wipes both Session State (P3: server crash wipes it) and Go registry | P4, P3 |
| D | Worker-process death only | Go OOM/panic/port-bind failure kills worker, Python `Popen` handle goes stale (`proc.poll()` non-None → `worker_alive()` falls to `/health`, `sidecar.py:77-90`); next `ensure_worker()` spawns a *fresh* worker with an empty registry, old `run_id` → `unknown run id` | `sidecar.py:75-90`, worker `unknown run id` string |
| E | Double-spawn / PORT fight | two Python processes (or a stale worker holding 6549) → second `Popen` succeeds as a process but fails to bind; depending on Go behavior the registry is either empty or split-brained; pump thread still tails the loser (`sidecar.py:93-115`) | `sidecar.py:149-160` |

Primary source: P1 (lines above) + P3 (per-tab Session State, wipe on server crash) +
P4 (12 h sleep deletes the container; 690 MB–2.7 GB memory band with slowdown/"Oh no"
symptoms) + worker-binary `unknown run id` literal.

Impact estimate: **medium-high severity, low-medium frequency**. When it hits, run loss
is genuine and unrecoverable (the data is nowhere but Go RAM). It is the correct
diagnosis for *some* "restarted" reports (stale tabs after sleep, post-OOM tabs), but F3
shows most reports need no restart at all. Rough split estimate: the majority of the
quoted errors at 200 rows are F2+F3 false positives; F4 dominates only across
sleep/OOM boundaries.

Suggested fix direction: persist the run registry server-side (worker-side disk store —
sqlite/file journal keyed by `run_id` — or a Python-side snapshot cache sufficient to
resume display); expose worker `boot_id`/uptime so the panel can distinguish "same
worker, slow poll" from "new worker, run truly gone"; on suspected loss, re-probe
`/health` + boot-id before condemning the run; document the 12 h sleep boundary in the
check-section caption.

## F5 (rank #5) — per-tick render + payload cost at 200 rows: full snapshot in, full DOM out, every 4 s

Cause: each tick downloads the *entire* run snapshot, scans all 200 results in Python
(usually twice), rebuilds the summary, and re-emits ~25 HTML cards plus a summary card
with remote flag images — all of which Streamlit clears and redraws from scratch per
fragment rerun.

Evidence:

- `lib/services/sidecar.py:336-338` — full `GET /v1/check?id=` snapshot every tick
  (no delta/pagination params); `netinfo.py:14-17` full `r.read()` + `json.loads`
- `lib/sections/check.py:75-106` — `_summary_card(run)` iterates **all** results
  (done/alive/latency sort, country set) per tick
- `lib/sections/check.py:109-121` — `_filtered_sorted()` copies (`list(...)`) + sorts
  all results; called **twice** per cycle — inside the fragment (line 233) and again
  for the outside pagination (line 247, on full reruns)
- `lib/sections/check.py:234-240` — page slice (`PAGE_SIZE = 25`, line 21), then
  `st.markdown(_row_html(r))` per row; `_row_html` (`44-72`) embeds
  `<img class="uf5-flag" src="{FLAG_CDN}/...">` (`config.py:72`, `netinfo.py:145-150`)
  per row plus a `<img class="uf5-geocard-bg">` in the summary (line 84/216) — the
  browser re-resolves these on every redraw
- `lib/sections/check.py:224-229` — `st.progress(...)` + `st.markdown(_summary_card(...))`
  re-created every tick; empty-state caption at 237-238

Primary source: P1 (lines above) + P2 ("elements are cleared and redrawn on each
fragment rerun" — i.e. per-tick DOM replacement of progress + summary + 25 cards is by
design, not a bug, and its cost scales with emitted HTML).

Impact estimate: **medium**. Rough sizing (estimate): 200 rows × ~300–600 B JSON/row ⇒
~60–120 KB per poll payload; Python per-tick CPU dominated by JSON decode + 2×
copy/sort of 200 dicts + ~26 markdown renders — tens to low-hundreds of ms server-side
plus full client re-render of ~25 cards + ~26 CDN images every 4 s. Reads as jank/freeze
stacked on F1/F2, and grows linearly with row count (why 200 rows hurts and 20 do not).

Suggested fix direction: shrink per-tick work — server-side pagination or delta polls
(`since=`/page params) so steady-state ticks carry ≤25 rows; cache per-row HTML by
(row index, done-state, latency bucket); lengthen cadence once `done/total` passes a
threshold; keep flag `<img>` URLs stable across ticks so the browser cache can hit;
avoid re-emitting the summary card when only counts changed.

## F6 (rank #6) — Python-side retention grows per run; event stream is bounded (good), Go log file is not

Cause: each started run parks its full result set in Session State and keeps it until
replaced; the shared event buffer is correctly capped, but the on-disk Go log that
backs it grows forever and the per-spawn pump thread/pipe never closes until process
death.

Evidence:

- `lib/sections/check.py:161-166` — `st.session_state["uf5_check_run"]` retains
  `results` + `accepted` + `rejected` + `detail`; `run.update(...)` at line 207-209
  swaps in the latest full snapshot but the previous large list is retained until GC
  and `accepted` (a copy of the submit payload) is never dropped
- `lib/core/events.py:19-22` — `log_event` appends then `del events[:-500]`:
  **bounded ring of 500, not a leak** — explicitly clearing this suspect
- `lib/core/events.py:25-63` — `ingest_go_events` tails from `uf5_go_offset`
  (per-session; first ingest per session seeks to last 32 KB, `GO_LOG_TAIL_BYTES`,
  `config.py:61`)
- `lib/services/sidecar.py:93-115` — `_pump_worker_logs` appends JSON lines to
  `GO_LOG_PATH` (`config.py:59`, default `/tmp/uf5vmjt-go.log`), `f.flush()` per line,
  no rotation/truncation anywhere in the panel
- `lib/services/sidecar.py:149-160` — one daemon pump thread + `stdout=PIPE`
  (`text=True, bufsize=1`) per spawn; never closed by the panel
- Display already caps `rejected[:100]` (`check.py:185`) — the raw list in state is not
  capped

Primary source: P1 (lines above) + P3 (Session State persists for the tab lifetime, so
retained snapshots accumulate across repeated runs within one tab).

Impact estimate: **low-medium**. One 200-row run is single-digit MB at most in
`uf5_check_run` — not itself an OOM. The risk is cumulative: repeated runs per tab +
500 events + an unbounded `/tmp` log on a 690 MB–2.7 GB Cloud box (P4) steadily raise
pressure toward the F4-C reboot cliff. The pump thread is one-per-spawn (cheap), but a
wedged child holding a full pipe buffer can pin its thread + fd indefinitely.

Suggested fix direction: drop `accepted` after start (or keep counts only); keep only
the latest run (or last N with explicit cap); rotate/truncate the Go log
(size-or-time-based, e.g. keep last ~1 MB); close/recycle the pump thread when the
child exits; keep the 500-event cap as is.

## F7 (rank #7) — widget-remount churn in check is already mitigated; sibling sections show the original pattern

Cause (residual): the check fragment is currently read-only by design (comment at
`check.py:179-181`), but every tick still recreates output elements (by fragment
contract), and the repo's other fragments still mount *interactive* widgets inside the
tick — the pattern the check comment says caused the earlier "freeze" (focus
steal/dropped clicks).

Evidence:

- Mitigated in check: filter/sort widgets live outside the fragment (`check.py:188-194`),
  pagination outside (`check.py:244-260`), fragment body is poll + progress + summary +
  rows (`check.py:201-242`)
- Still recreated per tick inside `_live`: `st.progress` (224-225), `st.error` (226-227),
  `st.markdown` summary (229), per-row `st.markdown` (239-240), `st.caption` (238) —
  P2 says this clear+redraw is expected fragment behavior, i.e. the F5 cost, not focus
  theft
- Original pattern visible next door: `lib/sections/logs.py:21-62` builds
  `segmented_control`, `button("Clear")`, `multiselect`, `segmented_control`,
  `time_input` ×2 **inside** `@live` (`logs.py:20-21`, `run_every=2` at line 16);
  stats tabs use `run_every=2/5` fragments (`stats.py:118-122`) with stale-section
  guards (`stats.py:126-129`, `logs.py:23-24`)
- Old-version fallback: `try: live = st.fragment(run_every=...) except TypeError:
  live = st.fragment` (`check.py:196-199`, `stats.py:118-122`, `logs.py:15-18`) — on a
  Streamlit too old for `run_every` the check poll runs **once** and the run sits at
  "running" forever. Installed here is 1.63.0 (supports it — signature verified), so
  dormant, not active.

Primary source: P1 (lines above) + P2 (widget interaction inside a fragment reruns the
fragment; elements cleared/redrawn per rerun).

Impact estimate: **low for check as of today** (the move-outside fix is in place and
should stay); informational for logs/stats. If freeze reports persist after F1–F3 are
fixed, the logs-section fragment is the next widget-churn suspect, not check.

Suggested fix direction: keep the check layout as is (do not move widgets back inside);
apply the same outside-fragment discipline to the logs fragment when it is next
touched; pin/require a Streamlit floor that supports `run_every` so the fallback branch
cannot silently disable polling.

## F8 (rank #8) — base full-rerun blockers raise the freeze floor on every navigation

Cause: several boot/render-path calls block the main script thread on every full rerun
with multi-second timeouts, independent of the check section. They do not cause the
200-row freeze by themselves, but they add a constant ~1 s+ latency floor that makes
every freeze feel longer.

Evidence:

- `main.py:57` → `ensure_worker()` → `worker_alive()` → `/health` with `timeout=1`
  (`sidecar.py:83-90`) on **every** full run, plus `trigger_tailscale_update()` with a
  `timeout=3` POST (`tailscale.py:42-49`) and a `timeout=2` status probe
  (`tailscale.py:63-68`) in `main.py:47`
- `lib/services/versions.py:115-123` — versions row resolves inside
  `with st.spinner(...)` per label; subprocess probes carry `timeout=10`
  (`versions.py:57` tailscale, `versions.py:83` sing-box); verdict fetches `timeout=3`
  (`sidecar.py:188,227,266`)
- `lib/sections/stats.py:52-56` — `time.sleep(0.5)` between `/proc` snapshots on the
  render path; `render_versions()` runs on the stats page (`stats.py:195-199`)
- `lib/services/netinfo.py:103-142` — keepalive/disambiguate probe (`timeout=8` at
  lines 86, plus `fetch_json` default 8 at line 14) once per session
  (`netinfo.py:112-114`)

Primary source: P1 (lines above) + P5 (each `timeout=N` is N seconds of main-thread
block worst case) + P3 (full reruns execute all of this top-to-bottom).

Impact estimate: **low-medium**. Typical added latency per full rerun ≈0.1–1 s when the
sidecar is warm (health << 1 s), spiking to 1–10 s when it is cold/down (health timeout,
tailscale POST timeout, subprocess timeouts). Worth fixing after F1–F3, not before.

Suggested fix direction: keep verdict caches (already in `sidecar.py:183-185`,
`222-224`, `262-264`, `versions.py:111-123`); move cold probes (health, tailscale
trigger, version resolvers) into fragments/threads or gate them behind longer TTLs;
replace the 0.5 s CPU sleep with non-blocking delta sampling.

## Consolidated ranking (by impact, rough)

| Rank | Finding | Kind | Estimate |
|------|---------|------|----------|
| 1 | F1 start blocks script ≤30 s (submit freeze) | freeze, deterministic | seconds–30 s per 200-line submit |
| 2 | F2 poll timeout 5 s > 4 s cadence (overlap/queue) | freeze, load-dependent | backlog after ~2 slow polls; whole-run jank at 200 rows |
| 3 | F3 miss counter aliases 3 modes to "restarted" | wrong diagnosis | 5 misses ≈ 20 s; fires on slowness alone |
| 4 | F5 full-snapshot + full-DOM re-render per tick | jank scaling with rows | ~60–120 KB/poll + ~26 markdown re-renders per 4 s tick |
| 5 | F4 genuine registry loss (sleep/OOM/new proc/worker death/PORT fight) | real data loss | infrequent per tab, permanent when it hits |
| 6 | F8 full-rerun blockers (health 1 s, tailscale 3 s, subprocess 10 s, sleep 0.5 s) | latency floor | ~0.1–1 s warm, up to ~10 s cold, per full rerun |
| 7 | F6 retention growth + unbounded Go log | slow pressure toward F4-C | MBs per run; unbounded `/tmp` log |
| 8 | F7 widget churn (check already fixed; logs fragment still inside) | residual/informational | none active in check; next suspect is logs |

Note on F4 vs F3 for the reported incident: a 200-line submit that spins ("разбирает")
and ends in "restarted, run lost" without any sleep/OOM gap is signature F1→F2→F3, not
F4. F4 should only be the leading hypothesis when the error follows a tab reopen,
a 12 h idle gap, or a Cloud "Oh no"/reboot event.
